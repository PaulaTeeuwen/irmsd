# Fe4Cage: the equal-mass axis fallback for mass-biased pre-alignment

## Test structure

`Fe4Cage.xyz`: a T-symmetric metal-organic cage, 316 atoms, 4 heavy Fe atoms among otherwise light organic ligands (C/H/N/O).

`min_rmsd` picks its pre-alignment strategy based on `nunique`, the number of atoms with a **unique canonical rank**
(no symmetry-equivalent twin anywhere in the structure). With 3 or more such atoms, it anchors a direct quaternion fit
on them, since 3 non-collinear, unambiguously-corresponding points are enough to fix a rigid-body rotation outright.

A highly symmetric structure, such as Fe4Cage, will not have any atoms with unique canonical rank (`nunique = 0`).
This means that every atom has a symmetry-equivalent partner elsewhere in the structure.
This forces an alignment using the principal axes (`axis`/`axis_0`) instead 
and resolves the remaining axis-labeling ambiguity with a 32-way grid search.

## Problem

These pre-alignment steps (`axis`/`axis_0`, `axis_module.f90`) weigh its inertia tensor by real isotopic mass. 
A small number of heavy atoms among many light ones can dominate that tensor and pull the resulting principal axes away from the structure's actual ones.

11 distinct isomers were generated by [`generate_pointgroup_isomers.py`](generate_pointgroup_isomers.py), 
which uses irmsd's own `get_symmetry_operations` to find them directly from `Fe4Cage.xyz`, and stored in `pointgroup_isomers.json`.
It holds the 11 distinct, non-identity elements of this structure's T point group (4×`C3`, 4×`C3²`,
3×`C2`), each an exact point-group operation (a simple rotation).

Before the fix, `get_irmsd` scored only 10/11 of them correctly (worst case ~2 Å), despite them being exact symmetry operations.
Specifically, one single `C3` element was wrong. The other three `C3`, all four `C3²`, and all three `C2` elements were
already exact even with the bug.

Note that this is a different failure mode from genuine axis degeneracy (e.g. C<sub>60</sub> and adamantane), 
which is still an open limitation where equial weighting does not help.

## Solution

Relabeling the 4 Fe atoms as Zn (also heavy) reproduces the failure at similar severity, 
while relabeling them as H (light) resolves the problem. This confirms that the failure stems from a mass mismatch.

`axis_0_equal_mass` / `axis_4_equal_mass` (`axis_module.f90`): 
identical to `axis_0`/`axis_4`, except every atom is weighted equally in the inertia tensor instead of by its real mass.
The only change is replacing `atmass = ams(at(i))` with `atmass = 1.0_wp`.

`min_rmsd` (`irmsd_module.f90`) now runs its existing pre-alignment + 32-way grid search (`min_rmsd_rotcheck_permute`) **twice**: 
once mass-weighted as before, and once with the equal-mass axes. 
It keeps whichever alignment reaches the lower LSAP cost. The grid search itself is untouched.
